# Improvements to Plan

## Context

I reviewed the active README in this snapshot at `docs/planning/README.md`, the full planning set under `docs/planning/`, and the current scaffold in `promptforge_services/` and `promptforge_watcher/`.

The architecture is sound: Obsidian intake, Python watcher, Postgres as system of record, n8n as orchestrator, deterministic Python preprocessing/validation/rendering, and llama.cpp for transformation. The main issue is not direction. It is plan drift. The docs describe a near-complete MVP, while the repo still contains only a thin starter scaffold.

## Suggested Improvements

### 1. Freeze one executable MVP slice

The plan should explicitly define the first runnable thin slice as:

`markdown note -> watcher parse/import -> preprocess -> validate -> render -> queued delivery record`

Do not treat n8n orchestration, llama.cpp integration, and live CLI dispatch as part of the first implementation hour. They are phase-two integrations after the deterministic core works.

### 2. Resolve contract drift before more coding

The docs currently disagree on key runtime contracts:

- `promptforge_docker_compose_mvp.yml` starts services with `python -m promptforge_api`, but the code exposes `promptforge_services.api:app`.
- Structured-output examples are inconsistent about `contract_name` and even the contract identifier itself.
- The review path is underspecified: `review_item_v1` exists, but review is not modeled as a first-class lifecycle in the same way as prompt generation and delivery.

The plan should add one canonical contract matrix covering:

- request/response payloads for watcher webhook and service endpoints
- required structured-output fields
- status transitions for `intake_notes`, `prompt_generations`, and `deliveries`
- exact behavior when `requires_review = true`

### 3. Add a field-ownership table

Right now frontmatter fields, DB fields, and generated fields blur together. The plan should state which fields are:

- Obsidian-only
- copied into Postgres
- resolved by deterministic Python code
- generated by the LLM
- generated during delivery/write-back

This will prevent watchers, services, and n8n from silently re-deriving each other’s state.

### 4. Make fixture-driven implementation the default

The project already has strong example assets:

- `promptforge_example_records.md`
- `promptforge_seeded_example_intake_notes.md`
- `promptforge_seed_data.sql`

The plan should convert those into executable fixtures and acceptance tests instead of leaving them as reference prose.

### 5. Narrow the next-hour success criteria

A realistic one-hour goal is not “implement the MVP.” It is:

- parse an intake note deterministically
- canonicalize approved directives
- persist or at least shape canonical records consistently
- validate one structured output contract
- render a final prompt from one template
- cover the happy path and one review/error path with tests

## Multi-Agent Plan For The Next Hour

### Working Rule

Use one lead plus three workers. Each worker owns a disjoint file set. Nobody reverts another worker’s changes. If a shared contract changes, the lead updates the canonical interface first, then workers adapt.

### Minute 0-10: Lead Contract Freeze

Lead owns:

- `improvements_to_plan.md`
- `pyproject.toml`
- interface notes for webhook/service payloads

Tasks:

- fix the canonical Python service entrypoint
- define the minimal endpoint payloads for `/preprocess`, `/validate`, and `/render`
- lock the first supported contract to `agent_task_v1`
- define the review fallback rule for unresolved project/target cases

Deliverable:

- one short interface note committed to the repo or pinned in the working thread

### Worker 1: Watcher And Intake

Owns:

- `promptforge_watcher/`

Tasks:

- implement note loading and content hashing
- parse frontmatter plus `## Control` / `## Transcript`
- add eligibility checks for `Inbox/Voice/`, `watch_eligible`, `status: new`, and non-empty transcript
- add deterministic directive parsing for the approved whitelist
- return canonical parsed-note and parsed-directive models

Target outcome:

- a fixture note can be parsed into stable Python objects without touching n8n

### Worker 2: Deterministic Services

Owns:

- `promptforge_services/`

Tasks:

- expand models beyond the current placeholder
- implement `/preprocess` for canonicalization and transcript cleanup
- implement `/validate` for `agent_task_v1`
- implement `/render` with one Jinja2 template path for `coding-cli`
- normalize output markdown

Target outcome:

- a canonical preprocessed transcript can become a validated rendered prompt

### Worker 3: Integration, Fixtures, And Smoke Tests

Owns:

- `tests/`
- `.env.example`
- `docs/planning/promptforge_docker_compose_mvp.yml`

Tasks:

- create fixture notes from the seeded examples
- add tests for note parsing, directive parsing, validation, and rendering
- fix the stale service startup command in Docker Compose
- add a basic smoke path for local `uvicorn` startup and module import

Target outcome:

- the repo has a repeatable local verification path, even if DB/n8n are still stubbed

### Minute 45-60: Lead Integration

Tasks:

- merge worker changes
- resolve any contract mismatches
- run `python3 -m compileall promptforge_services promptforge_watcher`
- run the new tests
- document remaining gaps: Postgres writes, webhook trigger, llama.cpp transform, delivery adapters, Obsidian write-back

### Expected End State After One Hour

If execution is disciplined, the repo should have:

- a real note parser
- a shared directive parser
- working preprocess/validate/render endpoints
- one supported rendered contract
- fixture-based tests for the happy path and one review/error path
- corrected local/container startup wiring

It should not be expected to have complete Postgres persistence, n8n orchestration, or real llama.cpp integration in that same hour. Those are the next integration wave after the deterministic core is stable.
